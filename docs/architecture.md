# Architecture — Technical Reference

This document describes the internal architecture and design decisions of AI Indian Rail Travel Assistant in more detail than the README.

---

## Two-Service Architecture

The project is intentionally split into two independently deployable services:

| Service | Technology | Deployment |
|---|---|---|
| Backend API | FastAPI + Uvicorn | Railway (Docker) |
| Frontend UI | Streamlit | Streamlit Community Cloud |

The split provides several benefits:

- **Security isolation**: API keys (`GEMINI_API_KEY`, `GROQ_API_KEY`) live exclusively in the backend environment. The frontend only knows the public backend URL.
- **Independent scaling**: the backend can be scaled or redeployed without redeploying the frontend.
- **Clear interface boundary**: the frontend communicates with the backend only through the documented REST API.

## Backend: FastAPI Application

### Entry Point (`main.py`)

`main.py` contains:

- The FastAPI application instance with title and version from `config.py`.
- A `lifespan` context manager that preloads RAG models on startup.
- A global exception handler that catches any unhandled server error and returns a clean JSON response (`HTTP 200` with `error: true`) so the frontend can always parse the body.
- Six route handlers: `GET /`, `GET /health`, `POST /stations/search`, `POST /trains/search`, `GET /trains/{train_number}`, `POST /chat`.

### Settings (`config.py`)

Settings are managed by `pydantic-settings` (`BaseSettings`). All fields are populated from:

1. Environment variables (checked first)
2. `.env` file (if present)

`extra = "ignore"` is set, so unknown environment variables do not cause errors.

Required fields (no default): `gemini_api_key`.  
Optional fields (have defaults): `gemini_model`, `groq_api_key`, `groq_model`, `app_name`, `app_version`.

### LLM Service (`llm_service.py`)

The `FallbackLLM` class wraps a primary (`ChatGoogleGenerativeAI`) and optional fallback (`ChatGroq`) LLM. It:

- Exposes `.invoke()`, `.bind_tools()`, and `.with_structured_output()` to act as a drop-in LangChain chat model.
- Detects quota errors using string matching on the exception message (`429`, `RESOURCE_EXHAUSTED`, `quota`, `rate limit`).
- Falls back transparently to Groq when Gemini hits a quota limit.

Three LLM variants are derived from `FallbackLLM`:

| Variable | Used For |
|---|---|
| `llm` | Base LLM used by agents |
| `intent_llm` | `llm.with_structured_output(UserIntent)` — returns a typed `UserIntent` object |
| `tool_llm` | `llm.bind_tools(railway_tools)` — used in some older code paths |

### Multi-Agent Graph (`tool_graph.py`)

The chat pipeline is a **LangGraph** `StateGraph` with the following nodes:

```
START
  └─→ intent_node        (classifies intent)
        ├─→ train_agent  (handles TRAIN_SEARCH, TRAIN_DETAILS, STATION_SEARCH)
        │     └─→ train_tools_node  (executes tool calls)
        │           └─→ train_agent  (loop until no more tool calls)
        ├─→ rag_agent    (handles RAILWAY_RULES)
        └─→ chat_agent   (handles GENERAL_CHAT)
```

**Conversation memory** is provided by `MemorySaver` (in-process). Each session has a unique `thread_id` (UUID generated by the frontend); LangGraph stores the full message list per thread.

**The `train_agent` uses a tool loop**: LangGraph's `tools_condition` conditional edge routes back to `train_tools_node` if the LLM emitted tool calls, and to `END` when the LLM emits a final text response. This allows the agent to call `station_search` and then `train_search` in sequence if needed.

**The `rag_agent` does not use an LLM decision loop**: it directly calls `railway_knowledge_search.invoke()`. This avoids an extra LLM API call and prevents the model from refusing to call the tool or hallucinating an answer before calling it.

### Older Graph (`graph.py`)

`graph.py` contains a simpler, earlier graph (`travel_graph`) that only handles train search via a fixed four-node pipeline: `extract_intent → resolve_stations → search_trains → build_response`. This graph is **not** used by the current `/chat` endpoint — `tool_graph.py` replaced it. It is preserved in the codebase but is not connected to any route.

## Data Layer

### Train Schedule Dataset

The CSV file at `data/railway/Train_details_22122017.csv` (≈16 MB) contains one row per train-station stop. Columns include: `Train No`, `Train Name`, `SEQ`, `Station Code`, `Station Name`, `Arrival time`, `Departure Time`, `Distance`.

`RailwayRepository` loads this file lazily using pandas and pre-groups it into a dictionary of `{train_number: sorted_route_dataframe}` for O(1) route lookups.

Train search works by:
1. Finding all rows where `Station Code` equals the origin code.
2. Finding all rows where `Station Code` equals the destination code.
3. Joining on `Train No` to find trains that stop at both.
4. Filtering to keep only rows where `SEQ` of origin < `SEQ` of destination (correct direction).
5. Computing journey duration by walking the route between origin and destination indices, accounting for midnight crossovers.

### Pandas as the Data Access Layer

The project uses pandas in-process rather than a database. This means:

- No database setup required for local development.
- The full ~16 MB dataset is loaded into memory once at first use.
- There is no persistent storage for user data or query logs.
- The `database.py` file exists in the backend directory but has zero bytes — it is unused.

## Frontend

The Streamlit frontend (`frontend/app.py`) is a single-file application. Key design points:

- **Session state** stores: `thread_id` (UUID), `messages` (chat history list), `pending_prompt` (button-triggered prompt), `manual_search_data` (last search form result).
- **`thread_id`** is generated once per session and sent with every `/chat` request to maintain conversation continuity in LangGraph's `MemorySaver`.
- **Pending prompt** mechanism: when a quick-prompt or follow-up button is clicked, the prompt is stored in `session_state.pending_prompt` and picked up on the next `st.rerun()`. This avoids Streamlit's widget-callback limitations.
- **Search context injection**: when a follow-up button is clicked after a manual train search, the search result summary is appended to the user's prompt as a `[Context from search results]` block. The frontend strips this before displaying the message in the chat history, but it is sent to the backend as part of the user message for context grounding.
- **Source rendering**: RAG answers containing `📚 Sources` are split into an answer section and a styled source box rendered with custom HTML/CSS.
- **Streaming simulation**: new assistant responses are displayed word-by-word using `st.write_stream()` with a small delay, giving the appearance of streaming even though the backend returns a complete response.

## Error Handling

| Layer | Mechanism |
|---|---|
| Backend global | `@app.exception_handler(Exception)` — returns `HTTP 200` with `error: true` in JSON body |
| Chat service | `chat_service.py` — catches `TimeoutError`, quota errors, permission errors, and generic exceptions with user-friendly messages |
| LLM fallback | `FallbackLLM` — automatically retries on quota errors with Groq |
| Frontend | `try/except` around each `requests.*` call — handles `Timeout`, `ConnectionError`, `HTTPError`, and generic exceptions with displayed error messages |

## File Naming and Import Pattern

Because the project supports both running via `uvicorn backend.main:app` (from the project root) and running individual scripts directly (e.g. `python backend/rag/vector_store.py`), most backend files use a dual-import try/except pattern:

```python
try:
    from backend.module import something
except ModuleNotFoundError:
    from module import something
```

`tool_graph.py`, `llm_service.py`, and `tools.py` also prepend the project root and backend directory to `sys.path` at import time using a path-walking loop so that relative imports work correctly regardless of the working directory.
